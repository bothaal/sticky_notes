# Research Answers

## 1. Preserving application state across HTTP request-response cycles

HTTP is a stateless protocol, which means the server treats every request as independent and keeps no memory of earlier requests from the same client. Web applications therefore need extra mechanisms to remember who a user is and what they have been doing. The most common mechanism is the cookie: a small piece of data the server sends in a `Set-Cookie` header, which the browser stores and returns with every later request to the same site. Rather than storing sensitive data in the cookie itself, most frameworks use server-side sessions. When a user logs in successfully, the server creates a session record (in a database, cache or file), generates a random session ID, and sends only that ID to the browser as a cookie. On each following request, the server reads the session ID, looks up the matching record and identifies the logged-in user. Django follows this approach: its `SessionMiddleware` manages the `sessionid` cookie, and its `AuthenticationMiddleware` attaches the authenticated user to `request.user`. Logging out deletes the session, so the old ID can no longer be used. Security measures are important because a stolen session ID can be used to impersonate a user. These include marking cookies `HttpOnly` and `Secure`, using HTTPS, setting session expiry, and creating a new session ID at login. An alternative, common in APIs, is token-based authentication, such as JSON Web Tokens (JWTs), where the client sends a signed token with each request.

## 2. Performing Django database migrations to a server-based database such as MariaDB

Django migrations are version-controlled files that describe changes to the database schema. They allow the structure of the database to be kept in step with the models defined in code. Moving from the default SQLite file database to a server-based database such as MariaDB involves several steps. First, MariaDB must be installed and running, and a dedicated database and user account with suitable privileges must be created, for example using `CREATE DATABASE` and `GRANT` statements. Next, a Python database driver is installed into the project's virtual environment; the `mysqlclient` package is the driver Django recommends. The `DATABASES` setting in `settings.py` is then updated to use the `django.db.backends.mysql` engine, which also supports MariaDB, along with the database name, user, password, host and port. Credentials should be loaded from environment variables rather than written into the code. Once the connection is configured, `python manage.py makemigrations` generates migration files from model changes, and `python manage.py migrate` applies them, creating the tables in MariaDB. `showmigrations` can be used to check which migrations have been applied, and `sqlmigrate` shows the SQL that a migration will run. If existing data must be moved from SQLite, it can be exported with `dumpdata` and imported with `loaddata` after migrating. Migration files should be committed to version control so every environment uses the same schema.
